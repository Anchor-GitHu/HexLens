## v1.5.0 — 疑似加密字段检测

**一句话**：打开文件时能指出"这段不是文件碎片，是一段需要密钥的密文"。

### 新增

- **`CipherFieldDetector`**：识别疑似加密载荷，判据全部是结构性事实
  - 无已知文件头 + 熵接近**该长度上限** + 长度规整（命中常见块长或摘要长度）+ 长度不大
- 输出的是**"该往哪找"而不是"这是 AES"**：
  - 提示块长（16 = AES/Serpent/Twofish/SM4 系；8 = DES/3DES/Blowfish）
  - 明确写出「**密文没有头部，任何声称能从字节直接看出算法的说法都不可信**」
  - 给出 CTF 里这类数据的常见来源与下一步动作
- 附带可执行动作：导出这段数据 / 在十六进制中查看

### 为什么这么做

在 BUUCTF `snake` 题上，图片尾部藏着一段 48 字节裸密文（Serpent-ECB）。当时工具只报了"尾部多出 394 字节"，
方向全靠人工摸索。这个功能就是为了补上那一步。

### 验证

- 核心测试 42 → **43**（新增 5 项断言：密文要报 ×2、文本/带头数据/过短不能报 ×3）
- 实测：48B 裸密文 / 随机 48B / 随机 256B 均报；JPEG、PNG、README、尾部附加 PNG 均不报

## v1.4.0 — 只读/编辑模式、文件头修复、PNG CRC、XOR 暴力破解

**一句话**：这一版补的是"**改完能验证**"——此前能自动识别，但不擅长安全地改。

### 新增

**① 打开方式询问**（用户提出）
- 打开文件或拖入时弹主题化对话框，问「编辑」还是「只读」
- `ByteDocument.IsReadOnly`，拦截点放在 **`Splice()`** —— 所有改动的最终汇聚点，连 `Undo`/`Redo` 都拦得住
- `OpenPathAsync(path, bool? editMode)`：`null` = 弹窗询问，显式传值 = 不问
  （命令行启动、自检、拖放必须传值，否则自动化场景会卡在等人点）

**② 文件头修复建议**
- 扩展名暗示类型 X 但文件头不是 X 的签名 → 线索卡片出现「改为 X 的文件头」按钮，一键写回
- `SignatureDatabase.GetByExtension` 按扩展名反查"本该是什么格式"

**③ PNG CRC 校验与修正**
- 遍历所有 chunk，重算 CRC32（覆盖「块类型 + 块数据」）并比对
- 给出每个坏块的「存的 vs 应是的」，支持逐块一键修正
- 背景：手改宽高/像素后 CRC 必错，而多数查看器遇 CRC 错**直接拒开**，看起来像"文件坏了"

**④ XOR 暴力破解**
- 遍历 256 个单字节密钥，按**结构性证据**打分：① 可打印字符占比 ② 开头是否撞上已知文件签名 ③ 是否含 `flag{...}`
- 「编码」页一键把选中的密钥应用到原区间

### 测试

- 核心测试 40 → **42**：新增「XOR 破解能挑出正确密钥」与「随机数据不该给出高置信候选」
  （后者是防假阳性：检测器最容易犯的错就是硬凑结果）
- **交叉验证**：PNG CRC 实现结果与 Python `zlib` 一致（同一坏块均算出 `0xA183E1BC`）

## v1.3.0 — 构建系统迁移到 CMake

**一句话**：一条 `cmake --build` 走完全程，删掉脚本式构建。

### 变更

- **顶层 `CMakeLists.txt`**：CMake 作为**编排层**
  - 原生编码库用 `add_subdirectory` 直接编
  - C# 侧因 CMake 无原生 C# 支持，用 `add_custom_target` 驱动 `dotnet CLI` 并显式声明依赖顺序
- 目标：默认（原生库→Core→App→Tests→跑测试）、`hexlens-core/-app/-tests`、`hexlens-test`、
  `hexlens-native-test`、`hexlens-publish`、以及子目录的 `ctfcodec` / `ctfcodec-cli` / `ctfcodec-tests`
- **删除 `scripts/build.ps1`**（职责已由 CMake 完整接管）
- ⚠️ **保留 `native/ctfcodec/build.ps1`** —— 那是原生库自带的独立构建脚本，可单独用 MSVC/MinGW 交叉验证

### 修复

- `enable_testing()` 移到**顶层**：只写在 native 子目录里时，`ctest --test-dir build` 会报 `No tests were found!!!`
- `.gitignore` 排除 CMake 构建目录

### ⚠️ 已知环境要求

**GNU 工具链（Ninja / MinGW Make）在 Windows 上处理不了非 ASCII 路径**，报错形如：

```
ninja: error: FindFirstFileExA(.../记事本/...): The filename, directory name, or volume label syntax is incorrect.
mingw32-make[2]: stat: .../common.cpp: Illegal byte sequence
```

**更坑的是它的表现：首次全新建能过，第二次增量构建必挂** —— 很容易误判成"偶发"。

**解法**：给项目建一个纯 ASCII 路径的 junction，然后从那里构建：

```powershell
New-Item -ItemType Junction -Path C:\HexLens -Target "<本项目真实路径>"
cmake -S C:\HexLens -B C:\HexLens\build -G Ninja
```

junction 对普通用户可用、完全透明，**产物仍落在真实目录**。

- **「数据检视」面板**（对标 010 Editor）：把选中字节按 uint/int/float/LEB128/GUID/多编码文本解释出来，
  同时列出**可能的编码**
- **Office 式编辑副本**：打开时在源文件同目录建立隐藏工作副本 `.名字.hexlens-work`，
  意外退出时副本还在，**原文件在整个编辑期间绝不是半截状态**
  - 保存采用三级降级：删除工作副本 → 直接写入 → 原子替换；仍失败则抢救到 `%TEMP%` 并明确报告

## v1.0.0 — 首个版本

**一句话**：CTF 向的十六进制编辑器，重点在**打开文件的瞬间就把可疑之处指出来**。

### 核心能力

**9 类自动线索**（按可能性排序，每条都带偏移、长度、依据与可执行动作）：

| 线索 | 说明 |
|---|---|
| 尾部附加 | 主文件声明范围之外还有数据 —— 最常见的"图种"藏法 |
| 内嵌文件 | 发现完整的 PNG/ZIP/ELF/PDF…… 并可一键导出 |
| 位平面 | 穷举位平面 × 通道 × 位序 × 扫描顺序后，从位流里直接扫出文件签名 |
| 位平面明文 | 位流里没有文件签名、但有明文（`flag{...}` 之类）—— CTF 里比藏整个文件更常见 |
| 疑似 Base64 | 长 Base64 串；解码后是文件或可读文本都会报出来，**带前缀也认** |
| 加密归档 | ZIP/RAR/7z 含加密条目，提示已知明文攻击思路 |
| 高熵区间 | 疑似压缩或加密数据的范围（附全局熵带） |
| 类型不符 | 扩展名与真实类型对不上 |
| 疑似反转 | 整份数据位反转/字节反转后就能正常解析 |

**6 个视图**：十六进制 / 结构 / 隐写 / 字符串 / 编码 / 熵·直方图

**识别是怎么做的**：

```
字节流
 ├─① 签名扫描      约 110 种文件头，单遍桶扫描（含掩码匹配，如 RIFF 家族）
 ├─② 长度推导      每个命中按格式算出边界：PNG→IEND、ZIP→EOCD、GZIP→deflate 末尾……
 ├─③ 嵌套判定      被别的文件区间包住 = 容器内部内容；在外面 = 可疑藏匿
 ├─④ 载体解码      PNG/BMP/GIF/WAV 自己解码出真实像素与采样（零外部依赖）
 ├─⑤ 位平面穷举    位平面 0–2 × 单通道/通道组 × 位序 × 行/列序 × 逆序
 ├─⑥ 结构化命中判定 命中必须靠近开头 **且** 长度可被结构推导 —— 否则视为巧合
 ├─⑦ 明文载荷判定   位流里没有文件签名时，找「最长连续可打印段」（≥20 字节）+ `flag{...}` 正则
 └─⑧ 线索引擎      把以上事实翻译成带动作的结论
```

第 ⑥ 步是准确率的关键。只按魔数判断的话，光是 ICO 的 `00 00 01 00` 就能在一份样本上刷出十条噪声
（实测：加这条判据前 **12 条命中、真命中 1 条**；加之后 **1 条命中、正是真载荷**）。
